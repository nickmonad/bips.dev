<h2>Abstract</h2>


This document specifies `rawtr()` output script descriptors.
A `rawtr()` descriptor expresses a Pay-to-Taproot output by its output key directly, without stating an internal key or a script tree.

<h2>Motivation</h2>


A taproot output key is derived from an internal key and an optional script tree, as described in <a href="/341" target="_blank">BIP 341</a>.
The `tr()` descriptor specified in <a href="/386" target="_blank">BIP 386</a> takes the internal key and the tree, and computes the output key from them.
There is no way to use `tr()` for an output whose internal structure isn't known, for example an output key received from another party, or one whose script tree the holder does not wish to reveal.
The `rawtr()` descriptor covers that case by taking the output key itself.

This expression has been implemented in Bitcoin Core since version 24.0, and <a href="/390" target="_blank">BIP 390</a> permits `musig()` inside `rawtr()` and uses it in its test vectors.
This document gives the expression a specification of its own.

<h2>Specification</h2>


A new script expression is defined: `rawtr()`.

The `rawtr(KEY)` expression can only be used as a top level descriptor.
It takes a single key expression as an argument and produces a P2TR output script.
Unlike `tr()`, it does not take a tree expression, and the key is used directly as the taproot output key, with no <a href="/341" target="_blank">BIP 341</a> tweak applied.

The output script produced is:
```
OP_1 <KEY>
```

Key expressions within a `rawtr()` expression must only create x-only public keys, as in `tr()` expressions.
Uncompressed public keys are not allowed. Compressed public keys are allowed, but will be implicitly converted to x-only public keys.
The keys derived from extended keys must be serialized as x-only public keys.

If the private key corresponding to the output key is known, the output can be spent via the key path.
Note that a `rawtr()` descriptor cannot show whether a script path exists for the output: nothing in it proves that the output key does not commit to a script tree.
Software importing a `rawtr()` descriptor from an untrusted source should warn that other spending paths may exist.

<h2>Rationale</h2>


No <a href="/341" target="_blank">BIP 341</a> tweak is applied to the key, since tweaking it would describe a different output than the one the descriptor is for.
The expression is top level only, because a P2TR output script is a complete scriptPubKey and there is no context in which it can appear as a sub-expression.

Key expressions are restricted to x-only public keys because a taproot output key is an x-only key.
Compressed public keys are accepted and converted implicitly, as in `tr()`, so a key expression written for one of the two also works in the other.

The absence of a specification has already produced divergence outside Bitcoin Core.
rust-miniscript renders these outputs as `rawtr_not_supported_yet(KEY)` and does not parse them back, and the bdk-ffi descriptor tests describe `rawtr()` as <a href="/386" target="_blank">BIP 386</a>, which specifies `tr()`.

<h2>Backwards Compatibility</h2>


`rawtr()` descriptors use the format and general operation specified in <a href="/380" target="_blank">380</a>.
This is a wholly new descriptor, and as such is not compatible with any implementation that predates it.
The scripts produced are standard Pay-to-Taproot scripts, so existing software is likely to be familiar with them.

<h2>Reference Implementation</h2>


`rawtr()` descriptors have been implemented in Bitcoin Core since version 24.0.
